# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone, Artificial Intelligence and Machine Learning Certification Program, E&ICT Academy, IIT Roorkee.
One repository, one branch (`main`). The data is synthetic (produced by `generate_data.py`); Delhivery is only the setting. Money is in Indian Rupees (INR).

The repository answers three questions in one connected pipeline:

1. How long will a parcel really take? (Part B, regression)
2. Which parcels will miss their promise? (Part C, classification and alert threshold)
3. Which hubs need which playbook? (Part D, K-Means segments, packaging, scoring script)

Part A cleaning and feature code (`src/shipment_prep.py`) feeds B, C and D, and the same two functions are re-used by `predict_delay.py`.

## How to run

From a fresh clone, in this order (every script runs from the repository root and uses only files in the repository):

```
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48  (writes data/hubs.csv, raw_shipments.csv, new_shipments.csv)
python part_a_clean_eda.py       # data/modelling_table.csv + outputs/part_a_*.csv
python part_b_regression.py      # outputs/part_b_*.csv
python part_c_classification.py  # outputs/part_c_*.csv
python part_d_segments.py        # outputs/hub_profile.csv, part_d_separation.csv, hub_segments.csv, segment_profile.csv, tier_vs_segment_mismatch.csv
python package_model.py          # models/*, outputs/part_d_reload_check.csv
python predict_delay.py          # outputs/new_shipment_actions.csv
```

`requirements.txt` pins `pandas`, `numpy`, `scikit-learn` and `joblib` with `==` (versions used: pandas 3.0.2, numpy 2.4.4, scikit-learn 1.8.0, joblib 1.5.3). `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt`; if your installed versions differ, re-run `package_model.py` instead of loading the committed pickle. Running `predict_delay.py` twice produces byte-identical output.

Repository layout: `generate_data.py` (verbatim), `data/`, `src/shipment_prep.py` (constants `PROMISED_HOURS`, `FEATURES`, `NOISE_COLUMNS`, plus `clean_shipments` and `build_features`), one script per Part, `package_model.py`, `predict_delay.py`, `models/`, `outputs/`.

## Data findings

Cleaning (`outputs/part_a_checks.csv`): 1,224 raw rows, 24 duplicates removed, 1,200 rows after de-duplication, all 1,200 survive the hub merge. Before filling: 36 missing `distance_km`, 24 missing `parcel_weight_kg` (plus 5 sentinel weights above 100 treated as missing), 12 missing declared values, 18 missing payment modes; `service_type` went from 12 spellings to 3. The 17 feature columns, `delivery_hours` and `is_delayed` have 0 missing cells afterwards. Medians used for filling: distance 314.95 km, weight 1.83 kg, declared value INR 1,121.50. Overall 278 parcels (delay rate 0.2317) are delayed.

1. **Service type.** Express is delayed most often: 119 of 243 parcels, a delay rate of 0.4897. Standard is 0.2056 and Economy 0.0857 (`part_a_delay_by_group.csv`).
2. **Hub tier.** The delay rate climbs steeply from Tier 1 (0.0400) to Tier 2 (0.2150) to Tier 3 (0.4400).
3. **Distance band.** Delay rate rises with distance: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km (75 of 88 parcels).
4. **Correlations with `delivery_hours`** (`part_a_correlations.csv`, ranked by absolute value, delivery_hours excluded): `promised_hours` +0.8372, `distance_km` +0.4013, `n_stops` +0.3247. (`hub_daily_capacity` at -0.3237 is a close fourth.)
5. **Why `declared_value_inr` was log-transformed.** On the median-filled column the mean (INR 1,533.05) is far above the median (INR 1,121.50), the sign of a right-skewed distribution, whereas after the natural log the mean (7.0277) and median (7.0224) are almost identical, so the log makes the feature roughly symmetric.

Also from the checks file: the IQR rule (bounds -0.7063 and 116.5238 hours from quartiles 43.255 and 72.5625) flags only 1 outlier in `delivery_hours`, so no rows were removed for outliers.

## Model results (regression)

All numbers from `outputs/part_b_*.csv`. Split: 840 / 180 / 180 rows. The scaler was fitted on training rows only: the largest absolute scaled column mean is 0 on the training rows and 0.2187 on the test rows, which shows the test rows were not used to fit it.

- **Baseline.** Predicting the training mean for every validation parcel gives R² = -0.0212 (RMSE 18.8552 hours). An R² of about zero (slightly negative) means the mean explains none of the variation in delivery time; any useful model must beat this.
- **Validation winner.** Linear regression won with an RMSE of 4.8912 hours (R² 0.9313, MAE 3.9222). Gradient boosting was very close (RMSE 4.9165, R² 0.9306), then random forest (5.5095, R² 0.9128) and the decision tree of depth 6 (6.2796, R² 0.8867).
- **Tree depth (bias versus variance).** Depth 1 is high-bias: train RMSE 11.6334 and validation RMSE 12.1324, both high, with a gap of only 0.4990 (it underfits). The best validation RMSE is at depth 6 (6.2796). With no depth limit the train RMSE is 0.0 but the validation RMSE is 7.8368, a gap of 7.8368, and depth 12 (train 1.3613, validation 7.3540) behaves the same way: these are high-variance (overfitting) trees.
- **Learning rate (gradient boosting, 100 trees).** Best is 0.1 (validation R² 0.9306, RMSE 4.9165). At 0.01 (R² 0.7127, RMSE 10.0018) the model learns too slowly: 100 small steps are not enough to get near the signal (underfit). At 1.0 (R² 0.8440, RMSE 7.3701) each step is so large that it overshoots and the model fits noise.
- **Cross-validation** (5 folds, one shared `KFold(n_splits=5, shuffle=True, random_state=42)` on the 1,020 training plus validation rows): linear regression mean R² 0.9261 (std 0.0048), gradient boosting 0.9353 (std 0.0045).
- **Final model and test score.** By the validation rule the final model is `linear_regression`, scored once on the test rows: RMSE 4.5235 hours, MAE 3.5671, R² 0.9493.
- **Which model I would ship.** The cross-validation ranking disagrees with the validation ranking: validation puts linear regression ahead of gradient boosting by only 0.0253 hours of RMSE, while cross-validation prefers gradient boosting by 0.0092 in R², about two standard deviations. A single 180-row validation set is noisy, whereas cross-validation uses all 1,020 rows five times, so I would ship gradient boosting: it can capture interactions a straight line cannot (for example the sale effect on Express parcels, or rain on long lanes). Linear regression stays a very strong, simpler fallback, and the test score reported above belongs to linear regression because the brief's rule fixes the final-test model by validation RMSE; the gradient-boosting model would be monitored in production before being trusted fully.

## Model results (classification)

All numbers from `outputs/part_c_*.csv`. Stratified split: 840 / 180 / 180 rows with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "not delayed" for every parcel gives validation accuracy 0.7667 (TN 138, FP 0, FN 42, TP 0), but recall is 0: it catches no delayed parcel, so it is useless for the one job the model has. Accuracy alone hides this because only about 23% of parcels are delayed. The three trained models reach validation accuracy 0.8833 to 0.9056 and F1 of 0.8046 (logistic regression), 0.7470 (decision tree, depth 6) and 0.7848 (default random forest).
- **Noise columns.** The five bookkeeping columns together hold 0.2245 of the 17-column forest's importance (the forest splits on them because impurity importance rewards continuous noise columns), yet all five fall outside the top 7 by F-score (ranks 8, 12, 14, 16, 17), and their F-scores are all below 10 (highest 4.5847). The top seven are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, `sale_event_flag`, and the lowest F-score among them is 36.7281.
- **Choice of k** (`part_c_selectk.csv`, validation F1): k=5 0.6988, k=7 0.8333, k=10 0.7857, k=12 0.8049, k=17 0.7848. Five columns throw away real signal (`rain_flag`, `sale_event_flag`); beyond seven the extra columns add mostly noise, so k = 7 is the best.
- **Tuning.** Grid search (27 candidates, 135 fits, best CV accuracy 0.8952) reached validation F1 0.7750 and randomized search (9 candidates, 45 fits, best CV accuracy 0.8905) reached 0.7848, while the untuned forest on the same 7 columns reached 0.8333. Tuning did not beat the untuned forest on validation. With only 42 delayed parcels in the validation rows, one or two parcels move F1 by several points, so differences of this size are within noise and tuning on a 180-row validation set cannot be trusted to find real gains. The final configuration is therefore `default_forest_same_7_features` (`SelectKBest k=7`, 100 trees, no depth limit, `min_samples_leaf` 1).
- **Alert threshold.** The operations rule (highest threshold with validation recall of at least 0.80) gives **0.5**: validation recall 0.8333 and precision 0.7955 (TP 35, FP 9, FN 7). At 0.6 precision rises to 0.8889 but recall falls to 0.7619, below the rule; at 0.4 recall rises to 0.8810 but precision drops to 0.7400, and at 0.1 recall is 0.9762 with precision 0.4824, which would mean many unnecessary calls.
- **Test result (scored once at 0.5).** TN 125, FP 14, FN 10, TP 31; accuracy 0.8667, precision 0.6889, recall 0.7561, F1 0.7209. Test recall (0.7561) is lower than validation recall (0.8333) and under the 0.80 target. With only 41 delayed parcels in the test set, a single parcel changes recall by about 2.4 points, so this gap is plausible sampling variation plus some optimism from choosing the threshold on validation; I report it as it is and do not re-tune.

## Operations recommendation

For the regional operations head (`outputs/hub_segments.csv`, `segment_profile.csv`, `tier_vs_segment_mismatch.csv`).

- **Escalate segment (9 hubs, mean delay rate 0.4600, mean delivery 64.6504 hours, mean distance 470.4757 km, mean 84.3444 stops):** Nagpur (HUB13, 0.46), Kochi (HUB15, 0.36), Patna (HUB17, 0.46), Ranchi (HUB18, 0.38), Guwahati (HUB19, 0.62), Raipur (HUB20, 0.48), Bhubaneswar (HUB21, 0.40), Siliguri (HUB23, 0.44) and Agartala (HUB24, 0.54). The Watch segment has 8 hubs (delay rate 0.1550) and the Standard segment 7 hubs (delay rate 0.0257).
- **Hubs whose tier label is misleading** (all four rows of `tier_vs_segment_mismatch.csv`): HUB07 Kolkata (Tier 1, behaves like Watch), HUB13 Nagpur (Tier 2, behaves like Escalate), HUB15 Kochi (Tier 2, behaves like Escalate) and HUB22 Dehradun (Tier 3, behaves like Watch). The tier label should not be used to choose the playbook; use the segment, which is based on observed delivery hours, delay rate, distance and stops. Nagpur and Kochi need the Escalate playbook despite being Tier 2, while Kolkata and Dehradun do not need the strictest or the lightest treatment their tier suggests.
- **Alert threshold: 0.5.** From `part_c_final_test.csv`, about 6.9 of every 10 flagged parcels are really delayed (precision 0.6889), and about 7.6 of every 10 delayed parcels are caught (recall 0.7561). The other delayed parcels (10 of 41 in the test rows) are missed.
- **New parcels** (`outputs/new_shipment_actions.csv`): of the 48 new parcels, 8 were flagged; 6 of those are in Escalate hubs and need a hub-manager escalation (Escalate to hub manager), and 2 get a proactive customer call. The other 40 need no action.
- **Why K = 3.** `part_d_separation.csv` shows the across-to-within ratio rising with K: 2.8940 (K=2, sizes 15-9), 5.3928 (K=3, sizes 9-8-7), 6.3047 (K=4, sizes 8-7-5-4) and 6.8866 (K=5, sizes 8-7-4-3-2). The jump from K=2 to K=3 (2.4988) is much larger than the gain from K=3 to K=4 (0.9119), and K=4 and K=5 both contain clusters of fewer than 6 hubs (4 hubs, and 4, 3 and 2 hubs), which is too small to carry its own playbook. K = 3 also matches the three playbooks operations actually runs, and its smallest segment still has 7 hubs.

## Production plan

**(a) Production-readiness characteristics mapped to the repository**

| Characteristic | Where it lives in the repository |
|---|---|
| Accuracy | Held-out evaluation in `part_b_metrics.csv` (test R² 0.9493) and `part_c_final_test.csv` (precision 0.6889, recall 0.7561, F1 0.7209); a threshold chosen to meet the recall rule |
| Reliability | `clean_shipments` handles duplicates, bad spellings, missing values, the sentinel weight and unknown payment modes; `new_shipment_actions.csv` has no missing value |
| Reproducibility | `generate_data.py`, fixed `random_state` values, pinned `requirements.txt`, one command order in "How to run", `package_model.py` regenerates the model |
| Performance (speed) | A 100-tree forest on 7 selected columns scores the 48 new parcels with a single `predict_proba` call; `predict_delay.py` needs no training step |
| Maintainability | One module `src/shipment_prep.py` for shared constants and functions, one script per Part, config in CSV files (`part_c_final_config.csv`) instead of hard-coded values |
| Consistency | Training (Part A) and prediction (`predict_delay.py`) call the same `clean_shipments` and `build_features`, with stored medians from `models/impute_values.csv` and the column order from `models/feature_order.csv` |
| Monitorability | `outputs/` holds baseline numbers (delay rate, flagged counts, thresholds) to compare against; `part_d_reload_check.csv` proves the saved model reproduces probabilities (difference 0) |

**(b) Quantities to monitor, with triggers**

1. Weekly delayed share of delivered parcels. Training baseline is 0.2317 (`part_a_checks.csv`). Trigger: more than 0.05 above or below baseline for two consecutive weeks (outside the sale window).
2. Weekly share of parcels flagged. In validation at threshold 0.5, 44 of 180 parcels (TP + FP in `part_c_thresholds.csv`) were flagged. Trigger: a weekly flagged share outside 0.15 to 0.35 on at least 500 parcels.
3. Recall on parcels whose outcome is now known. Test recall was 0.7561 and validation recall 0.8333. Trigger: recall below 0.60 over a rolling month with at least 50 delayed parcels, which means retrain and review the threshold at once.
4. Input drift: the share of missing `distance_km` (36 of 1,200 rows in training) and the mean of `distance_km` and `n_stops` per hub. Trigger: a missing share above 0.05, or a hub mean moving by more than one training standard deviation.

**(c) Retraining schedule, the sale window and drift**

Retrain monthly on the latest delivered parcels (re-running `package_model.py` and the Part C threshold rule on a time-based validation slice), and immediately when any trigger above fires. For the 15-28 September sale window (`sale_event_flag`), compare delay rate, flagged share and recall against the previous sale window (the same kind of event), never against ordinary weeks, because sales raise delivery hours (especially for Express) and a naive comparison would raise false alarms; ordinary-week monitors should exclude flagged sale days. After each sale, add its parcels to the training data. Data drift here would look like: longer average lanes or more stops per route (more parcels in the high-delay distance bands), a change in the service mix toward Express, a hub that starts behaving like a different segment (tier label and segment diverge further), a new hub missing from `hubs.csv`, more missing or sentinel values, or a clearly different share of rainy days (`rain_flag`) than in the training period.

## Limitations

1. **Synthetic data.** The data comes from a generator with simple additive effects, so real shipments will be noisier and the very high R² and the clean separation of noise columns will not carry over.
2. **Small test set.** The test rows contain only 41 delayed parcels, so test precision (0.6889), recall (0.7561) and F1 (0.7209) have wide uncertainty; one parcel moves recall by about 2.4 points.
3. **Threshold tuned on one validation split.** The threshold of 0.5 was picked on 180 validation rows (42 delayed) and the test recall (0.7561) fell below the 0.80 rule target, so the rule is not guaranteed to hold on new data.
4. **Random splits, not time splits.** Parcels from July to September are shuffled across train, validation and test, which is optimistic for a model that will predict future weeks, especially around the sale window.
5. **Small samples everywhere.** 1,200 parcels, 24 hubs (50 parcels each) and 48 new parcels; the hub segments come from only 24 profile rows, and K-Means results for K = 4 and 5 depend on the seed and hub order.
6. **Tuning noise.** Validation F1 differences between the tuned and untuned forests (0.7750, 0.7848 and 0.8333) are within the noise of a 180-row split.
7. **Pickle portability.** The saved model loads reliably only on the pinned scikit-learn version.
